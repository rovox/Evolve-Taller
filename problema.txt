Análisis de la Situación

   1. El Problema es Correcto: Tu diagnóstico es 100% acertado. Tu Light Node (celestia-node) está
      configurado para hablar con tu Consensus Node local (celestia-app) a través de la variable
      DA_CORE_IP="celestia-app". Como tu nodo local está desincronizado, no puede confirmar tu
      balance, y por lo tanto no puede firmar ni enviar "blobs" (transacciones de datos).

   2. La Solución es Correcta: Apuntar tu Light Node a un RPC público es la solución más rápida y
      eficiente para un entorno de desarrollo. Esto le dará acceso inmediato a una versión
      sincronizada de la blockchain para que pueda operar.

   3. ¿Qué Pasa con tu Wallet y Fondos?
       * Tu wallet (claves privadas) está almacenada en el volumen
         `da-celestia_celestia-node-data`.
       * La información desincronizada de la blockchain está en el volumen
         `da-celestia_celestia-appd-data`.
       * Tu wallet está segura. El plan de acción NO TOCARÁ el volumen
         da-celestia_celestia-node-data. De hecho, eliminaremos el otro volumen
         (celestia-appd-data) que ya no es necesario, liberando espacio en disco.

   4. ¿Qué Cambios se Necesitan?
       * Archivo `.env`: Hay que cambiar DA_CORE_IP y DA_CORE_PORT para que apunten al RPC
         público.
       * Archivo `entrypoint.da.sh`: El script de inicio del Light Node actualmente no está
         preparado para conectarse a un RPC seguro (HTTPS/SSL). El comando celestia light start
         necesita un indicador adicional (--core.grpc.ssl) para habilitar la conexión segura, que
         es necesaria para el RPC público.
       * Archivo `docker-compose.yml`: Actualmente, tu Light Node (da) depende de tu Consensus
         Node local (app). Como dejaremos de usar el nodo local, esta dependencia debe eliminarse
         para que el Light Node pueda iniciarse de forma independiente.

  Fase 1: Análisis Profundo de los Componentes Actuales

  Analicemos cada pieza de tu configuración para que no quede ninguna duda sobre qué hace y por
  qué está ahí.

  Imágenes de Docker y su Propósito:

   1. `busybox` (usada en el servicio init-1-permission)
       * ¿Qué es? Es una de las imágenes más pequeñas que existen. Contiene una colección de
         utilidades básicas de Linux (como chown, cp, ls). Es como una navaja suiza para tareas
         simples.
       * ¿Qué hace aquí? Su única misión es ejecutar el comando chown -R 10001:10001 /data-node
         /data-app. Esto corrige los permisos de los directorios dentro de los volúmenes,
         asegurando que el usuario con ID 10001 (el usuario con el que se ejecutan los
         contenedores de Celestia) pueda escribir en ellos. Es un paso de preparación para evitar
         errores de "Permission denied". Una vez que termina, se apaga.

   2. `ghcr.io/celestiaorg/celestia-app:v6.2.0-mocha` (usada en init-2-appd)
       * ¿Qué es? Es una versión específica y más antigua del Consensus Node.
       * ¿Qué hace aquí? Se usa solo para inicializar la configuración del nodo. Los proyectos a
         veces usan una versión fija para la inicialización para garantizar que la estructura de
         configuración sea siempre la misma, incluso si versiones más nuevas la cambian. Ejecuta
         el script entrypoint.init-2.sh para crear los archivos config.toml, genesis.json, etc.,
         dentro del volumen celestia-appd-data. Una vez que termina, se apaga.

   3. `ghcr.io/linuxserver/baseimage-alpine:3.22` (usada en init-3-snapshot)
       * ¿Qué es? Es una imagen genérica de Alpine Linux, ligera y con herramientas de red
         básicas.
       * ¿Qué hace aquí? El nombre del servicio, "snapshot", nos da la pista. Su script
         entrypoint.init-3.sh seguramente descarga una "foto" reciente de la blockchain (un
         snapshot) para acelerar drásticamente la sincronización inicial. En lugar de empezar
         desde el bloque 1, empieza desde un bloque muy reciente. Descomprime este snapshot en el
         volumen celestia-appd-data. Una vez que termina, se apaga.

   4. `ghcr.io/celestiaorg/celestia-app:v6.2.2-mocha` (usada en el servicio principal app)
       * ¿Qué es? Es la versión principal y más reciente de tu Consensus Node.
       * ¿Qué hace aquí? Este es el servicio que se ejecuta de forma permanente. Carga los datos
         y la configuración que prepararon los contenedores init-* y empieza a sincronizar con la
         red desde donde lo dejó el snapshot. Este es el servicio que está atascado y
         desincronizado.

   5. `ghcr.io/celestiaorg/celestia-node:v0.28.2-mocha` (usada en el servicio da)
       * ¿Qué es? Este es tu Light Node. Es el componente con el que tu aplicación Evolve
         interactúa.
       * ¿Qué hace aquí? Su trabajo es enviar y recibir datos de la red de Celestia. Para poder
         enviar datos (pagar el "gas"), necesita consultar el saldo de tu wallet, y para eso,
         pregunta al Consensus Node (app). Aquí es donde falla la cadena.

  Relación con Volúmenes y Red:

   * Volumen `da-celestia_celestia-appd-data`: Usado por init-1, init-2, init-3 y app. Contiene
     exclusivamente los datos del Consensus Node. Es grande, pesado y actualmente, inútil por
     estar desincronizado.
   * Volumen `da-celestia_celestia-node-data`: Usado por init-1 y da. Contiene la configuración
     de tu Light Node y, lo más importante, tus claves de la wallet. Es pequeño y vital.
   * Red `evstack_shared`: Es la red privada de Docker que permite que los contenedores se
     comuniquen entre sí por sus nombres de servicio (ej: el contenedor da puede encontrar al
     contenedor app simplemente llamándolo "celestia-app").
